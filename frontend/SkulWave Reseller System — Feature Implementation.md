# SkulWave Reseller System — Feature Implementation

Add a **Reseller/Voucher Sales System** to the existing SkulWave application.

Do NOT rebuild or replace the existing voucher, authentication, MikroTik, package, or redemption systems. Inspect and extend the existing implementation.

## 1. Core Idea

Instead of me generating and printing voucher batches for students who sell them, each approved reseller should have their own reseller account.

The reseller can:

1. Log in.
2. See packages available for resale.
3. Generate a voucher for a selected package.
4. See the generated PIN.
5. Sell the PIN to a student.
6. Mark the voucher as SOLD.
7. See their sales.
8. See their commission.
9. See how much money they currently owe SkulWave.
10. See previous payments/settlements.

The goal is to eliminate the need for me to manually generate and print voucher batches for resellers.

---

# 2. VERY IMPORTANT: Voucher Lifecycle

Use this lifecycle:

```text
GENERATED → SOLD → REDEEMED
```

Other possible states:

```text
GENERATED → CANCELLED
SOLD → EXPIRED
```

### GENERATED

Voucher has been created by the reseller but has NOT been sold.

It must NOT count as a sale.

### SOLD

Reseller has confirmed that they sold the voucher to a student.

Only at this point should the transaction be recorded financially.

### REDEEMED

Student has successfully used the voucher through the existing SkulWave/MikroTik redemption system.

### CANCELLED

Admin cancelled the voucher.

### EXPIRED

Existing voucher expiration logic determines this.

# 5. Reseller Voucher Generation

Create a simple reseller page:

```text
Generate Voucher

Package:
[ Select Package ]

[ Generate Voucher ]
```

Only packages that the admin has enabled for reseller sales should appear.

When the reseller generates a voucher:

1. Validate reseller is ACTIVE.
2. Validate package is active.
3. Generate voucher using the EXISTING voucher-generation mechanism.
4. Associate the voucher with the authenticated reseller.
5. Return the PIN and package information.
6. Set status to `GENERATED`.

Example:

```text
SKULWAVE

Package: Daily
PIN: 48273195
Price: GHS 2.00

Status: GENERATED

[ COPY PIN ]
[ MARK AS SOLD ]
```

The PIN should be easy to copy on a phone.

# 6. Reseller Ownership

Every voucher generated by a reseller must record:

```text
reseller_id
```

Admin-generated vouchers can have:

```text
reseller_id = NULL
```

Do not create a separate voucher system.

Extend the existing voucher model/table if appropriate.

---

# 7. Mark Voucher as SOLD

After selling the voucher, reseller clicks:

```text
MARK AS SOLD
```

Backend must:

1. Verify authenticated reseller.
2. Verify voucher belongs to that reseller.
3. Verify voucher status is `GENERATED`.
4. Change status to `SOLD`.
5. Record `sold_at`.
6. Create exactly ONE sale transaction.

This operation must be atomic and idempotent.

Double-clicking the button must never create two sales.

---

# 8. Financial Model

Each package should have:

```text
student_price
reseller_commission
skulwave_amount
```

Example:

```text
Student pays:       GHS 10
Reseller keeps:     GHS 2
SkulWave receives:  GHS 8
```

Therefore:

```text
skulwave_amount = student_price - reseller_commission
```

Do not hardcode these values.

Use the existing package configuration where possible.

---

# 9. IMPORTANT: Save Price Snapshots

When a voucher becomes SOLD, save the financial values into the sale transaction:

```text
student_price
reseller_commission
skulwave_amount
```

Do NOT calculate historical transactions from the current package price.

Example:

Today:

```text
Package = GHS 10
Commission = GHS 2
SkulWave = GHS 8
```

If the admin later changes the package to:

```text
Package = GHS 12
Commission = GHS 2.50
SkulWave = GHS 9.50
```

the old sale must remain:

```text
GHS 10
Commission GHS 2
SkulWave GHS 8
```

# 16. Existing Redemption System

Do NOT change the existing student voucher redemption flow unnecessarily.

When a student successfully redeems a reseller voucher through the existing system:

```text
voucher.status = REDEEMED
sale.redeemed_at = current timestamp
```

The financial transaction should NOT be created at redemption.

It was already created when the reseller marked the voucher SOLD.

Therefore:

```text
GENERATED
    ↓
SOLD
    ↓
Financial sale created
    ↓
REDEEMED
```

A reseller still owes SkulWave for a voucher they sold even if the student never redeems it.

# 17. Security

The backend must calculate all financial values.

Never trust frontend-submitted:

```text
price
commission
skulwave_amount
reseller_id
```

Frontend should only need to submit something like:

```json
{
  "package_id": 123
}
```

The backend retrieves the package and calculates everything.

Also ensure:

- Passwords are hashed.
- Reseller routes require authentication.
- Admin routes require admin authorization.
- Resellers can only access their own records.
- Resellers cannot modify prices.
- Resellers cannot modify sales.
- Resellers cannot create duplicate sales.
- Voucher PINs remain unique.
- Suspended resellers cannot generate vouchers.
